The key structural point

The two workloads that normally dominate a biometric attendance bill — face matching and map rendering — both run locally at zero marginal cost. Face descriptors are compared in-process, and tiles are served by OpenStreetMap. There is no per-check-in API meter running today.

02Why the backend is free — the Azure grant

With minReplicas: 0, the container is only billed for the seconds it is actually serving. Between check-ins the app scales to zero and the meter stops. That is what makes an intermittent field-attendance workload a good fit: a system used twice a day costs almost nothing in compute, because it is asleep the other 23 hours.

03What it costs as it scales

Compute is driven by how many seconds the container is actually awake. The model below assumes 0.5 vCPU and 1 GiB per replica, 40 seconds of active replica time per check-in (face upload, verification, geofence evaluation, record write, plus dashboard activity), and two check-ins per employee per working day across 22 working days.

Two things worth reading off this table:

  • Up to roughly 170 employees the compute bill is genuinely $0. At 100 employees the system uses about 59% of the free vCPU grant, so there is real headroom before anything is charged.
  • Requests never become a cost driver here. Even at 500 employees the system uses about 13% of the 2 million free requests. The free grant would not be exhausted until roughly 3,800 employees — more than 7× the current compute ceiling, so compute will always run out first.
Sensitivity to the 40-second assumption

That figure is the single lever that moves the compute number. If a check-in completes in 15 seconds instead of 40 — a warm replica, a smaller photo payload, a tighter verification path — divide the 250- and 500-employee rows by about 2.7. The 250-employee case drops to under a dollar a month; the 500-employee case to about $3.90.

Attendance records are small — a few hundred bytes each. At 500 employees the database grows by roughly 5 MB per month, so the 500 MB Supabase ceiling is a multi-year horizon on records alone. The limit that arrives first is file storage (1 GB) if check-in photos are retained.

The real Supabase constraint is not size — it is the pause

Supabase pauses a free project after 7 days without a database request. A paused project is unavailable until someone logs into the dashboard and unpauses it manually. For a system used on working days this is mostly a weekend-plus-holiday risk, but a long break would take the app offline. The standard fix is a scheduled keep-alive ping (a GitHub Actions workflow or an uptime monitor), which costs nothing. Pro at $25/month removes the pause entirely and is the right upgrade the moment real staff depend on the system.

07What would actually trigger a bill

In order of likelihood, these are the events that move the cost off zero:

  1. Relying on the system for real payroll. This is the trigger for Supabase Pro at $25/month, not a technical limit — it is the purchase of "the database will never pause and will be backed up daily".
  2. Growing past roughly 170 employees on the current compute allocation. This is a soft ceiling, raised by shrinking the replica or shortening the per-check-in work.
  3. Adding a managed face-matching API. $3.40/month at 100 employees, $21/month at 500.
  4. Adding SMS notifications. The single most expensive per-unit choice available — $58–264/month at 100 employees.
  5. Retaining check-in photos. Supabase file storage is capped at 1 GB on the free plan, and this is the ceiling reached first. Offloading photos elsewhere or expiring them on a schedule keeps this at zero.

08Required fixes before any deployment

These are not billing items, but they are prerequisites for the cost plan above to hold. All three are open right now.

1. The database URL is IPv6-only and will fail on most hosts

DATABASE_URL points at db.fwmjwjgeajwpnmxeqbyv.supabase.co, which has no IPv4 address at all — verified by DNS lookup. It works on this development machine only because it has IPv6. Any IPv4-only host (Vercel functions, many container networks) cannot connect, and the failure appears as a generic connection timeout rather than a clear DNS error. The fix is to repoint to the Supabase pooler, which does have IPv4 — the working endpoint was confirmed by an actual connection test:

DATABASE_URL=postgresql://postgres.fwmjwjgeajwpnmxeqbyv:[PASSWORD]@aws-0-ap-northeast-2.pooler.supabase.com:6543/postgres

Note the username must carry the project reference (postgres.<ref>), not a bare postgres.

2. The database connection timeout is too aggressive for a remote host

backend/src/config/database.config.ts sets connectionTimeoutMillis: 2000. Two seconds is fine on a warm local link (the measured handshake was ~511 ms) but marginal from a remote region, where a cold connect plus TLS handshake can exceed it. This is the most likely cause of the intermittent Connection terminated due to connection timeout errors seen on login. Raise it to 10000.

3. The Vercel rewrite still points at a tunnel

dashboard/vercel.json proxies /v1/* to a temporary trycloudflare.com tunnel that will expire. Once the backend has a permanent Azure URL, that destination must be updated, and APP_CHECKIN_URL in the backend environment must point at the final dashboard URL.
